# 工作流断点恢复、严格门禁与智能受理 - 需求规格说明书

> 阶段：Specify。本文件只定义"做什么"，不写任务分解与实现方案。

## 概述
- **摘要**：为现有五阶段规格驱动工作流增加三项能力：断点可恢复、阶段严格顺序门禁、自然语言智能受理（自动分类、复制模板、从 develop 建分支）。
- **目的**：让工作流在中断、切换 AI agent/会话后能无损续跑；杜绝跳阶段；把用户开工成本降低为"用一句话描述需求"。
- **目标用户**：仓库的人类开发者与所有 AI 编码代理。

## 目标
- 任何阶段中断后，全新 agent 仅凭仓库内产物即可确定"在哪断、下一步做什么"并继续，不重走已完成阶段。
- 五个阶段严格串行：上一阶段退出条件未全部满足，不得进入下一阶段。
- 用户输入需求时系统自动判定类型（修复 / 新需求交付），自动取号、复制对应模板、从 develop 拉取并创建分支。

## 非目标
- 不改变五阶段的定义与最终通过标准（独立 Review pass 仍是唯一成功出口）。
- 不引入任何外部工具、插件或 CI 系统；全部机制由 Markdown 约定 + git 命令完成。
- 不做远端 push、PR/MR 自动化。
- 不实现自然语言分类模型，分类由关键词规则 + 歧义时一次询问完成。

## 背景与上下文
- 现状（奠基决策见 `docs/adr/0001-adopt-spec-driven-workflow.md`）：五阶段已定义，模板位于 `.trae/specs/_templates/{spec,tasks,review}.md`，分支约定为 `spec/NNNN-slug`，无状态记录文件，无 develop 分支，开工需手动取号复制。
- 痛点：阶段进度只散落在文档内容里，agent 切换后只能靠推断；"何时算阶段完成"无显式清单；用户每次开工要手动做目录/分支操作。

## 功能需求
- **FR-1 断点状态卡**：每个特性目录内新增一个机器/人可读的状态文件，至少记录：编号、类型、slug、当前阶段、下一动作、当前任务、更新时间、交接备注、五阶段门禁勾选记录。
- **FR-2 恢复协议**：新 agent 接手时按"查 INDEX → 读状态卡 → 校验产物与门禁一致性 → 从下一动作续跑"的固定流程恢复；发现状态与产物矛盾时以产物为准并修正状态。
- **FR-3 阶段门禁清单**：为五个阶段分别定义进入前置条件与退出清单；状态卡中每阶段退出必须逐项勾选并留时间/证据，未满足禁止推进。
- **FR-4 智能受理分类**：受理用户输入时，命中修复类关键词（包含但不限于"修复、优化、bug、报错、异常、崩溃、故障、不工作、失败、缺陷、慢、卡、回归"）判定为**问题修复**，否则判定为**新需求交付**；无法确定时只向用户询问一次。
- **FR-5 自动建产**：确定分类后自动完成：INDEX 取号 → 依据输入生成英文 kebab-case slug → 复制对应类型模板目录 → 从 `develop` 分支创建工作分支。
- **FR-6 分支基线**：所有工作分支一律从最新 `develop` 创建；新需求用 `feature/NNNN-slug`，修复用 `fix/NNNN-slug`；`develop` 不存在时先由初始化基线创建。
- **FR-7 双模板**：模板分 `feature`（完整规格）与 `fix`（轻量：问题现象/复现/根因/修复方案，验收以回归 rule 为主）两套，均含 spec/tasks/review/状态卡四件。

## 非功能需求
- **NFR-1 低门槛**：一个从未读过细则的用户，仅凭根 README 的受理说明，用一句话即可开工，全过程不需要手动取号、复制、建分支。
- **NFR-2 自包含可恢复**：恢复所需信息全部在仓库文件内，不依赖会话记忆；状态卡单文件不超过一屏。
- **NFR-3 向后兼容**：`_templates` 旧扁平结构被新结构取代后，所有文档中的路径引用同步更新，无死链。

## 约束
- **技术**：仅 Markdown + git；文档语言中文，代码/文件名/分支名英文。
- **业务**：不 push 远端；首次基线提交需经本次计划批准。
- **依赖**：本机 git 可用（仓库已 git init，尚无提交）。

## 假设
- 接受 `feature/`、`fix/` 取代旧的 `spec/` 分支前缀（旧约定尚无任何分支使用，无迁移成本）。
- 修复类需求仍走完整五阶段，只是模板更轻、验收以回归 rule 为主，不跳过 Review。
- 编号序列对 feature/fix 共用一套全局四位序号。

## 验收标准

### AC-1：状态卡与恢复协议可支撑无损续跑
- **Type**：`rule`
- **Given（给定）**：一个进行中的特性目录（任一阶段）
- **When（当）**：一个全新、无会话记忆的 agent 接手
- **Then（则）**：它能通过 INDEX 与状态卡确定当前阶段、下一动作、当前任务，并按文档规定的恢复协议续跑，且不重复已完成阶段
- **Pass Condition（通过条件）**：两套模板均含状态卡文件且包含 FR-1 全部必填字段；`.trae/specs/README.md` 含明确恢复协议步骤；产物路径存在且字段齐全（用文件检查取证）
- **Evidence（证据来源）**：模板文件内容、工作流 README 恢复协议章节、目录清单

### AC-2：阶段严格串行门禁成文且可核验
- **Type**：`rule`
- **Given（给定）**：工作流指南文档
- **When（当）**：检视五阶段定义
- **Then（则）**：每个阶段有进入前置条件与退出清单，且明确"退出清单未全部勾选不得进入下一阶段"，状态卡含对应的五阶段勾选区
- **Pass Condition（通过条件）**：文档中五阶段均有 Entry/Exit 清单项；状态卡含五个门禁勾选项；README 明确禁止跳阶段
- **Evidence（证据来源）**：`.trae/specs/README.md` 门禁章节、状态卡模板

### AC-3：智能受理分类规则明确
- **Type**：`rule`
- **Given（给定）**：一句中文需求输入
- **When（当）**：执行受理流程
- **Then（则）**：命中修复类关键词判为 fix，否则判为 feature，歧义时只询问用户一次
- **Pass Condition（通过条件）**：受理章节列出关键词集合、默认判定规则、歧义询问规则，三类样例各至少一条
- **Evidence（证据来源）**：工作流 README / 根 README 受理章节文本

### AC-4：受理自动化四步可照做且模板双轨就位
- **Type**：`rule`
- **Given（给定）**：用户给出一句需求
- **When（当）**：按文档执行受理
- **Then（则）**：自动完成取号、生成 slug、复制对应模板、从 develop 建分支四步；feature 与 fix 两套模板目录存在且各含四件
- **Pass Condition（通过条件）**：文档给出可照抄的命令序列；`_templates/feature/` 与 `_templates/fix/` 各含 spec.md、tasks.md、review.md、状态卡四个文件
- **Evidence（证据来源）**：目录清单、模板文件、受理章节

### AC-5：分支全部基于 develop
- **Type**：`rule`
- **Given（给定）**：本地仓库
- **When（当）**：查看分支基线约定与实际分支
- **Then（则）**：约定要求工作分支一律从 develop 创建，且本地存在 develop 分支
- **Pass Condition（通过条件）**：`git branch` 输出含 develop；AGENTS.md 与工作流 README 均写明"从最新 develop 建 feature/fix 分支"及命令
- **Evidence（证据来源）**：`git branch` 输出、AGENTS.md、工作流 README

### AC-6：低门槛受理说明质量
- **Type**：`rubric`
- **Dimension（维度）**：新用户仅凭 README 完成首次受理的顺畅度
- **Scale（量表）**：1-5
- **Anchors（锚点）**：1 = 仍需阅读多个文件或手动操作才能开工；3 = 照着做可完成但有歧义步骤；5 = 一句话需求 → 全程自动化受理，步骤无歧义、含分类样例与续跑说明
- **Pass Threshold（通过阈值）**：>= 4
- **Evidence（证据来源）**：根 README 受理章节、工作流 README，评审者模拟首次使用

## 待澄清问题
- 无（分支前缀替换、修复仍走五阶段、共用编号序列三项假设在此明示，批准视为接受）。
