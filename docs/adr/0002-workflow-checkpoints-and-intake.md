# 0002. 工作流断点状态卡、严格阶段门禁与智能受理

- 状态：Accepted
- 日期：2026-09-27

## 背景（Context）

ADR-0001 确立了五阶段规格驱动工作流，投入实际使用前暴露出三个问题：

1. **不可断点续跑**：阶段进度只隐含在文档内容中，会话中断或切换 AI agent 后，新上下文只能靠推断决定"做到哪了"。
2. **阶段边界可被跳过**：缺少每个阶段"满足什么条件才算完成"的显式清单，存在未批准先实施、未清空队列就评审的风险。
3. **开工门槛高**：每次都要手动取号、复制模板、建分支；且用户的修复诉求与新功能诉求没有分流，修复类被迫填写重型模板。

## 决策（Decision）

四项机制成文，全部仅依赖 Markdown + git，不引入外部工具：

1. **断点状态卡 `state.md`**：每个特性目录第四件套，记录编号、类型、slug、分支、当前阶段、下一动作、当前任务、更新时间、交接备注与 S1-S5 门禁勾选。阶段切换或任务状态变化时立即更新；恢复时"查 INDEX → 读状态卡 → 校验产物一致性（矛盾以产物为准）→ 按下一动作续跑"。
2. **严格串行门禁**：五阶段各自定义 Entry 前置条件与 Exit 退出清单；Exit 未全部勾选并写入 state.md，禁止进入下一阶段。
3. **智能受理 Intake**：用户一句话开工；命中修复类关键词（修复/优化/bug/报错/异常/崩溃/故障/失败/缺陷/慢/卡/回归等，含英文同义词）判为 fix，否则判为 feature，歧义只问一次；自动完成取号、复制模板、初始化状态卡与 INDEX 登记。模板分 `feature`（完整规格）与 `fix`（复现/根因/回归，验收以回归 rule 为主）双轨。
4. **develop 基线与分支命名**：`main` 为基线、`develop` 为集成分支；一切工作分支一律从最新 develop 创建，命名 `feature/NNNN-<slug>` 或 `fix/NNNN-<slug>`，取代 ADR-0001 中的 `spec/NNNN-<slug>`（该前缀从未实际使用）。feature/fix 共用一套四位编号。修复类同样走完整五阶段，不跳过 Review。

## 后果（Consequences）

- 正面：中断/换人可无损续跑且防伪造进度（状态卡须与产物一致，矛盾以产物为准）；跳阶段在制度上被封死；用户开工成本降为一句话；修复类有合身的轻模板与回归测试硬要求；develop 基线保证各工作分支从同一集成点出发。
- 负面/代价：每次状态变化多一步写卡纪律，依赖代理自觉与 Review 校验；关键词分类可能误判（如"优化代码结构"实为重构），以"歧义只问一次"和可人工纠正兜底；纯本地仓库不做 develop 与远端同步。
- 后续行动：首个真实 feature/fix 验证双模板合身度；若分类词表需要增删，更新本 ADR 与工作流 README 的词表（保持两处一致）。
