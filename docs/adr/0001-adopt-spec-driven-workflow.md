# 0001. 采用规格驱动工作流与分层目录架构

- 状态：Accepted
- 日期：2026-09-27

## 背景（Context）

`simulation` 是全新 Python 项目，长期将由人类与 AI 协作开发。需要解决两个问题：

1. AI 协作中需求容易在对话里丢失、验收标准模糊、实施者自验即收尾，质量缺乏独立门禁；
2. 需求产物、代码、测试、决策记录若混放，随着模块增多将难以追踪"某个行为是哪条需求、哪轮评审确定的"。

备选方案：

- A. 直接编码，靠提交信息和口头约定追踪 —— 轻但不可追踪，评审无据可依；
- B. 规格与代码分仓 —— 隔离彻底但上下文切换成本高、易过期；
- C. 单仓内规格驱动，规格产物与代码分层共存（本方案）。

## 决策（Decision）

采用方案 C，仓库按职责分层：

- `.trae/specs/NNNN-<slug>/`：按特性隔离，每个特性内聚 `spec.md`（做什么）、`tasks.md`（怎么做与证据）、`review.md`（独立评审）；
- `src/simulation/`：业务代码（src-layout）；`tests/`：测试；
- `docs/adr/`：跨需求的架构决策记录；
- `AGENTS.md`：人与 AI 的协作铁律。

工作流固定为五阶段门禁：**Specify → Plan → Approve → Implement → Review**；未批准不实施，队列清空才评审，独立评审 `pass` 是唯一完成出口。

## 后果（Consequences）

- 正面：每条代码变更可回溯到 AC 与评审证据；需求边界（spec）与实现拆解（tasks）分离；评审独立性制度化；新成员/新 AI 会话可凭目录快速重建上下文。
- 负面/代价：每个特性多三件文档的流程开销；对琐碎变更是负担 —— 已在工作流指南中定义豁免（纯文案、依赖补丁等 `chore` 类变更）。
- 后续行动：首个正式特性创建时按 `.trae/specs/README.md` 开工；如流程在实践中需要裁剪，以新 ADR 修订本记录，而非口头偏离。
