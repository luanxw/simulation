# 0003. 项目常驻授权、S6 自动交付与可选评审者

- 状态：Accepted
- 日期：2026-09-27

## 背景（Context）

ADR-0002 建成断点状态卡、严格门禁与智能受理后，用户在首次实战中提出三点：① 工作区内每次增改与 S3 批准都要停顿确认，链路频繁中断；② Review pass 即结束，缺少保证"评审与收尾产物全部入库"的交付步骤；③ 评审者固定为同类全新子代理，带界面或跨模块的需求无法选择具备相应能力的 agent。

## 决策（Decision）

1. **项目级常驻授权**：本仓库工作区内的文件增/改/删、测试、本地 commit、建本地分支与阶段推进无需逐次确认；**S3 由人工强制批准改为自动批准**——代理自检 spec/tasks 后在对话中给出摘要即继续，并在 state.md 留授权痕迹。用户保留**随时否决权**，否决即回退对应阶段。
2. **唯一强制确认点 = 远端写**：`git push`、创建 MR/PR 必须取得用户当次明确确认；S6 及任何阶段只做本地提交。force-push、`reset --hard`、删分支、工作区外改动始终禁止。
3. **新增 S6 Deliver**：S5 最近一轮 pass 后自动执行——提交 review/state/INDEX 等全部收尾产物、确认 `git status` 干净、置 Done 并输出交付摘要。流程由五阶段变六阶段：S1→S2→S3(自动)→S4→S5→S6。
4. **评审者可选**：state.md 增加"评审者指定"字段；默认全新 general_purpose_task 子代理，用户可在 S5 前指定 browser_use、search 等 agent；独立性三不变（未参与实施、只读、出带 Result 的 R 轮次报告），整改后每轮换新评审者。
5. **分支例外留痕**：0001 已 Done 未及合并 develop，0002 经用户当次明确批准沿用 fix/0001-workflow-resume-and-intake 分支连续落地；此为例外，"工作分支一律从 develop 切"的常规不废止，例外必须在 state.md 与 ADR 记录。

## 后果（Consequences）

- 正面：从一句话受理到收尾提交全程无人化阻断，交付节奏最快；评审与台账变更不再有"通过了但没入库"的灰色地带；评审视角可按需求类型匹配（浏览器实测、检索核查等）；push 单点确认兼顾效率与远端安全；用户用随时否决权替代逐次批准。
- 负面/代价：需求方向的人工卡点由"强制前置"变为"可随时打断"，依赖用户在 S3 摘要出现时保持注意；代理越权风险集中到远端操作，故 push 门禁与破坏性操作禁令必须长期保留；六阶段使状态卡/模板多一个勾选项。
- 后续行动：配置远端后 push 门禁自动生效；如需恢复人工 S3 或调整授权范围，以新 ADR 修订本记录；用户指定非默认评审者的首批案例用来补充 agent 适用场景清单。


## 补充：S7 Merge（2026-09-28）

用户补充需求：push 成功后须自动创建 Merge 请求并返回链接。据此流程扩展为七阶段：**S6 Deliver（本地收尾提交，不 push）→ S7 Merge（用户当次确认 push 后执行：推送 → 建 MR → 返回链接）**。要点：
- MR 创建优先 `gh pr create --base develop`；gh 缺失/未登录时输出托管平台的预填建 MR 链接（GitHub compare 链接）兜底，两者均满足"返回链接"；
- 目标分支默认 develop；MR 的合并按钮始终由用户自行点击，代理不代合并；
- 唯一强制确认点不变：push 仍需当次明确确认；确认一次后，push 与建 MR 连续自动执行，无二次停顿。
